# 实施问题支持（impl-support）

用户描述现场/项目中的具体问题（联调失败、进度卡点、客户加需求、硬件未到位等）时使用。

## 流程

1. **澄清 3 点**（信息够则跳过）：项目名、现象、已尝试什么。  
2. **检索库**（1～2 次）：  
   - 项目实施方案 / 进度 / 阶段（`doc_type=products` 或方案文档）  
   - `docs-vault/meeting/` 历史决议（`doc_type=meeting`）  
   - FAQ / 参数表中的约束  
3. **按阶段给动作**（对齐库内里程碑，如启动→调研→开发确认→培训→试运行→交接）：

```markdown
## 问题理解
## 库内依据
- `path` § …
## 建议处理步骤
1. 立即（24h 内）：…
2. 短期：…
3. 需要客户配合：…
## 边界与风险
- 若超出合同/方案范围：走变更，不在现场口头扩
## 升级路径
- 内部：项目经理 / 产品 / 研发
- 对外：书面确认后再实施
```

## 原则

- 优先对齐**已写进实施方案的流程**，不发明新流程冒充公司标准。  
- 库内无先例时：给「通用工程做法」并标注 **「非文档库依据，需内部确认」**。  
- 涉及加功能、加接口、加工期：明确 **范围变更**，提示补会议纪要 + `rag_reingest`。  
- 涉及医疗业务风险（数据、安全、诊疗流程）：建议升级，不替代院方制度。

## 禁止

- 指导绕过等保/院内安全制度  
- 承诺库内没有的远程驻场/工期  
- 伪造「公司已规定」流程  

## 入库闭环（重要）

问题定性后，建议用户把结论写成纪要（`meeting-ingest`）并 `rag_reingest`，下次同类问题可检索。
